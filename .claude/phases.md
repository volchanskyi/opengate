| EF-C2: where an alert lands, and what a purge owes the room it leaves | Alerts had a transport and nowhere to land — `handleAgentAlert` validated one, logged a line and returned. Three tables give them a home, and each answers a question that is easy to get wrong in a way nothing notices for months. **Evidence is a column on the alert row, written in the same statement**: not a side table and not an object key, both of which make "the alert is here and its evidence is not" a state the system can reach — and since there is no path for asking the endpoint again, such a row reads as a complete record of something nobody can reconstruct. Its cap and the codec-always-named rule are **check constraints**, proven by a forced failure rather than by reading the code. **Identity is `(device, rule_id, rule_version, window_start)`**, never the id the device chose: an agent that lost its local store picks a new one and would duplicate every alert it still had to send, so a reconnect replay is a no-op — not an error, not a second row. The **500/hour ceiling is the customer's**, rolling rather than calendar, and evaluated **inside the insert**, because a count taken beforehand and an insert taken afterwards see different rows and a storm on several connections at once is exactly when that gap opens; at the tenant, Contoso's bad night would spend Fabrikam's budget, and silencing an estate's detection is worse than the storm. Suppression is counted twice and folded once — a typed drop so the ingest ledger balances, `opengate_alerts_suppressed_total` for the operator, and one storm room carrying the count, because a number on a dashboard is not a line in a triage queue. Alert clocks are **refused rather than clamped**: the window start *is* the identity, so pulling it to a bound would land one alert on a different row every reconnect. And the erasure half — the whole substance of C8 — is the part the foreign key cannot do: purging DAL-WS-012 takes its alerts and evidence, but `occurrences` and `device_count` are application state, so they are **restated from the surviving rows before the cascade runs** (recomputed, not subtracted, because a purge is resumable), leaving 39, and a room the erasure empties is closed with a `resolution` event and no cause code. Alerts now join the ingest ledger with ten `alert_*` reasons of their own. | — | [edge-first-c2-alert-store-and-ingest.md](plans/archive/edge-first-c2-alert-store-and-ingest.md) |
| EF-C1: an alert that carries its own evidence | An alert used to be three fields riding a health summary, and everything behind it lived on the machine that raised it. That is a contradiction now that central keeps a 60 s average per dimension and there is **no path for asking the endpoint afterwards**: whatever is not on the alert at fire time does not exist anywhere. So `AgentAlert` is the alert transport, and the **only** one — a second would be a second source of truth for the same event — and it carries [`AlertEvidence`](../agent/crates/mesh-protocol/src/control.rs) with it. The composition is **fixed rather than "top-N by whatever fits"**: eight ranked dimensions, the top three of them with their readings ±5 min around the event, ten processes, twenty redacted log lines. Fixed because two of Contoso's incidents a fortnight apart are only comparable if they were assembled the same way — a technician who reads `disk.await_ms 0.91` on FS01 and `disk.await_ms 0.62` on DAL-WS-012 has to be reading the same measurement. **Size is decided after encoding, because compressed size is not knowable before it:** evidence over the 64 KB cap gives up its least valuable parts in a fixed order — log samples, processes, series readings, whole series, and the ranking last and never entirely — re-encoding after each step and setting `truncated`. Going over the cap costs the alert its tail; it never costs the alert, because a machine in trouble still has to be able to say so. That forced the conflict this phase existed to find: the evidence cap and the server's telemetry payload bound named **the same 64 KB**, so a maximal alert would have been refused for carrying exactly the evidence it is supposed to carry. The alert path now has **its own** bound, sized as the evidence cap plus a stated envelope allowance ([`conn_alerts.go`](../server/internal/agentapi/conn_alerts.go)), rather than borrowing a number from a path with different risk. **`deflate-1` costs neither side a dependency** — the agent already has pure-Rust `miniz_oxide` for the local store's cold tier and the server reads it with stdlib `compress/flate` — and the codec is **named on the message rather than assumed**, so a later one is additive and a reader that does not know one says so instead of decoding nonsense. `(device, rule_id, rule_version, window_start_ts)` identifies an alert independently of the id the device chose, so a reconnect replaying a queued alert resolves to the row already written; an alert missing any part of that identity, or carrying a severity outside `Info | Warning | Critical`, is refused at ingest under **its own counted reason** rather than stored under a null that would duplicate on the next reconnect. `severity` and `backfilled` are always on the wire, so "nothing said" and "not serious" never look alike. The hostile-corpus redaction assertion earned its keep: a mounted share carries `user:pass@host` with **no scheme in front of it**, so the shared redactor's `://` test read a password in a UNC path as ordinary text — closed at the redactor, where every caller benefits, not at the alert. | — | [edge-first-c1-alert-wire-and-evidence.md](plans/archive/edge-first-c1-alert-wire-and-evidence.md) |
| EF-B11: a rule that turns out to be wrong, and the machine that pays for it | Two gates already stopped a rule that is malformed (the closed grammar) or unaffordable (the CI cost bound). Neither touches a rule that is valid, affordable and **wrong** — Contoso's `disk-slow` shipped two milliseconds too tight, and all 380 of their machines raise it through the nightly backup window before anyone reads the first one. A rule now reaches an estate in **stages** — the larger of five machines and 1 %, then a tenth, then all of it — held **1 h** and **6 h**, where **the hold is a minimum and never a trigger**: what advances a rule is the estate having stayed quiet while it was held, and a hit alert ceiling, a machine that stopped the rule for costing too much, or a rule that failed to evaluate sends it **back one stage and restarts that stage's clock**, so a signal that comes and goes cannot ratchet a rule back up. A rule already on its smallest population **halts** there rather than being pulled off the machines proving it; ending it is a **kill**, which is a person's decision and not a timer's. The gate reads its signals through an injected port and never approximates one, because a gate on a made-up signal looks like protection. Stage membership is computed **per machine** from the machine, the rule and the reach — no roster — so it answers the same on every server and across a restart, and growing a rollout only ever *adds* machines; the five-machine floor is bounded by the fleet and holds for every partial stage, and a customer's estate is counted only while they are mid-rollout. **`kill` is a row, not a release**: it stops the rule at the next push for a connected machine and at reconnect for an offline one, and it outranks the stage. On the endpoint, the machine enforces **its own ceiling over what a rule actually touched** — the same figure the pack is bounded by, so the two gates cannot disagree — stopping the rule **per rule** (one expensive rule must not silence the cheap ones), **hard** (no retry until a different rule arrives, so a flaky link cannot re-spend the allowance) and **reported** as a fourth coverage state, `throttled`, which is liveness and deliberately not `unsupported`: a mistuned rule is not a permanent platform gap on a customer's remediation list. | EF-B10: has this happened before, and how far back the device can answer | A rule arriving on a machine answered "is this happening now"; the question an operator asks in the same breath is "has this been happening", and it turns a newly written rule from a guess into something with evidence behind it — Contoso installs `disk-slow` after DAL-WS-012's NVMe finally failed, and the useful reply is "four of your machines have been drifting like that one was", not "no drives are slow this second". Answering it centrally means a third storage path holding ~5.5 GB per 48 h at fleet scale for only 48 h of reach, so it is answered **on the machine**, against the minute-by-minute rollups the local store already keeps ([`retro.rs`](../agent/crates/mesh-agent-core/src/alerts/retro.rs)). **History is only asked what it can answer:** a rule about a span shorter than one stored minute is reported as one history cannot answer rather than evaluated at the wrong resolution, and for the rest the reading taken from each minute follows the rule's own question — a **sustained** rule reads the minute's least favourable reading, so a finding means every second of it was past the line; a rule with **no sustain** reads the peak, which answers "was it ever crossed" exactly; a window max reads the peak and a window mean the mean, both exact reconstructions. The direction is deliberately the one that cannot invent an episode, because a scan reporting something that did not happen costs more trust than one missing a marginal case. Every finding is stamped with the minute it **happened** — scan time would fold a three-week-old freeze into today and make a whole scan look simultaneous — and one scan's findings share **one grouping key**, so learning a new failure mode yields one incident per `(rule, scope)` rather than paging a queue once per episode. The scan is scheduled around the machine rather than the queue: chunks bounded in stored readings, a stand-down between them sized from a duty budget well inside the agent's own, and a full stop during maintenance, on a busy host, and while the host disk fills — the disk threshold derived from the store's own footprint policy, so the scan stands down **before** eviction starts trading history for space (which also wired the store's free-space backoff to a real reading of the host disk for the first time). It resumes from a durable cursor by re-reading a bounded window before it and suppressing findings from behind it, so a stopped scan produces exactly what an uninterrupted one would; and a rule is scanned **once per version, not once per push**, with each scanned definition remembered in full — the server pushes the whole ruleset on every reconnect, so triggering on the push would re-raise every historical finding whenever a flaky link came back, and a digest that changes with a toolchain would do the same after an agent upgrade. Findings spend the device's ordinary alert allowance through the one bounded sink, because a scan matching thousands of minutes is exactly the flood that ceiling exists for. **Q11 answered by measurement, not division:** a store driven through the production write path until its cap is evicting and then asked for its oldest surviving minute, at 2/4/8 MiB, where the reach scales with the cap to within 5 % — which is what makes the extrapolation to the shipped 512 MB cap evidence rather than the same arithmetic in a new coat. The answer is **~7 months** at 13 series × 1 Hz and ~2.3 B per stored reading: months rather than the "years" the central-versus-edge comparison claimed, still two orders of magnitude past a 48 h central recorder, so that verdict holds and the claim is restated as measured. [ADR-072](../docs/adr/ADR-072-retroactive-rule-evaluation.md). | — | [edge-first-b10-retroactive-evaluation.md](plans/archive/edge-first-b10-retroactive-evaluation.md) |
| EF-B9: where a rule lives, and what a customer may change about it | The grammar said what a rule may express; nothing said where a rule lives, who may retune it, or how a customer stops one. Those are three questions with three answers, and answering them together is what goes wrong — a threshold is exactly what an operator retunes (Contoso runs `disk-critical` at 90, its file servers fill by design and want 95, DAL-WS-012 is a workstation where 90 is right), while a *predicate* decides what every endpoint in every estate computes on every sample, which is not configuration but code with a cost. So a rule now has **three layers separated by how mutable each one is**. Definitions — predicate, grammar, evidence spec, `group_by`, `group_window`, shipped numbers — are versioned YAML [`go:embed`-ed](../server/internal/rules/catalogue/) into the server, **immutable per `(rule_id, version)`** against digests committed in `catalogue.lock`, so the rule that raised an alert last week still means what it meant then and editing a published definition is refused at load rather than by convention; a YAML typo is a build failure, not a runtime 500, and there is deliberately no load-from-disk fallback. That placement is the whole point: it keeps the program's highest-impact gate in CI, where **`rule_cost` is bounded per rule *and* across the whole pack** — a per-rule ceiling alone does not bound an endpoint, since enough rules just inside it still sink one — and where a rule that would ask 5 000 endpoints to hold an hour of samples costs one engineer a minute instead. Customer **bindings** live in Postgres carrying only values the rule declares tunable, validated against that rule's own bounds **on write** so a number nobody would want is refused while an operator can still see why, and they resolve device → site → organization → tenant → shipped through the ladder that already exists rather than a second copy of it. **Each parameter resolves on its own**, so a customer-wide sustain window survives one machine's retuned threshold — resolving a binding as a unit silently drops the sustain, which is the loss nobody notices until an alert does not arrive — and the file-server-at-95 case therefore needs no special machinery: put the file servers in a site. A binding may also carry a bounded tag selector with an operator-set `precedence`, and **two selectors at one rung sharing a precedence cannot be stored at all**, so resolution never depends on the order rows came back in. **Rollout state** lives in Postgres because stopping a rule cannot require a deploy; a customer with no row **has not configured the rule and gets it as shipped**, since reading absence as "switched off" leaves a fresh customer unmonitored while looking healthy, and `kill` stays separate from `enabled` because an ordinary choice and an intervention have to be distinguishable afterwards. An unreadable store is **reported rather than replaced with the shipped defaults** — substituting them pushes rules that ignore a kill switch at exactly the moment somebody reached for one, and the agent keeps the ruleset it already holds. Coverage is now **stored by the nature of each state rather than together**: `active`/`unknown` are liveness and stay in memory (FS01, decommissioned three weeks ago without anyone saying so, reads `unknown` — exactly true, where a stored `active` would claim 500/500 machines watched when the real number is 499), while `unsupported` is a durable fact about an estate and is persisted under two rules — **only `unsupported` is ever written**, so a device reporting `active` *deletes* its row rather than flipping it and **steady state costs zero writes**, and deleting a device erases its rows by cascade or a decommissioned container inflates the count forever. Contoso's monthly "how much of the estate is blind to `io-stalled`?" now answers the same on Tuesday as on Monday. All three tables carry forced RLS through **one shared `app_tenant_visible` predicate** — stated once so an edit cannot reach two tables and miss the third — plus a composite `(tenant_id, organization_id)` key, so a row naming another tenant's customer is refused by the database rather than by a check somebody has to remember to run. [ADR-071](../docs/adr/ADR-071-rule-catalogue-bindings-and-durable-coverage.md). | — | [edge-first-b9-rule-catalogue-and-bindings.md](plans/archive/edge-first-b9-rule-catalogue-and-bindings.md) |
| EF-B8: what a rule may say, and which machines it is watching | A rule was four fields over three metric names, and both halves were wrong for a curated pack. The names were the pre-rename ones (`mem.used`, `disk.used`) while the vitals had moved on, and every rule the grammar could express was one instantaneous reading crossing one line — which states none of the failures that motivated the pack. DAL-WS-012's NVMe drifts 2 ms → 40 ms over a fortnight and no second of it crosses a line anyone would set in advance; FS01's 02:00 backup runs 28 I/Os deep at a healthy 3 ms while a device in trouble runs 28 deep at 40 ms, and **one number cannot separate them, nor can two rules that fire independently**. Three additions and no more — **rate of change, window `max`/`mean`, and cross-dimension conjunction** — with comparators, `sustain_secs` and hysteresis unchanged, so a rule declaring none of them is exactly the rule the fleet already runs. The constraint that shaped all of it: an agent executing server-supplied code is a supply-chain weapon aimed at every customer estate, so the grammar grows but never into a language. [`rule_cost`](../agent/crates/mesh-agent-core/src/alerts/evaluator.rs) answers what any rule costs from its declared fields alone — monotone in the window, summed over conditions — and **a predicate whose cost cannot be computed statically is one the grammar cannot express**, which is why the window and term count are bounded constants and why an ill-formed shape (window past the bound, a windowed predicate with no window, an instant one carrying a window it would silently ignore) is refused by name rather than attempted. Conjunction is **one rule, not two**: two rules page twice for one condition and the operator reading the queue alert cannot know the service-time alert exists; its hysteresis clears as soon as **any** side recovers past its own boundary, which with a single condition is exactly the hysteresis that shipped. **A partial window is not-enough-data, not a fire** — a warming-up rule is `active`, not `unsupported`, and firing on nine of ten seconds would page someone for every agent restart. The vitals names became canonical with `mem.used`/`disk.used` accepted as **aliases**, resolved in one place per side and pinned together by `go_control_push_alert_rules.bin` — the server generates it from its own vocabulary and the agent decodes it asserting the resolved set is **exactly** its own, so a name either side adds alone fails the test; a breach always names the canonical metric, and the server resolves the same way inbound, so an agent from before the rename and one from after write **one series rather than two halves of one story**. Coverage (I8) makes silent partial coverage impossible: per rule every device is `active`, `unsupported` or `unknown` and the three always sum to the fleet, with `unsupported` a **first-class state rather than an error path** — treating "this kernel publishes no pressure information" as a failed evaluation yields `unknown` and hides a permanent platform gap behind a transient-looking label. It rides `AgentHealthSummary` additively as `rule_coverage[]`, omitted when empty — which is also the shape an agent that predates it sends, so the existing golden is byte-identical and doubles as the forward-compat fixture — and rides the periodic anomaly summary too, because a calm machine emits no breach summary and a rule watching nothing on a quiet fleet would otherwise be invisible. **No coverage table in this phase:** coverage is a liveness view, so states are held in memory per connected agent and `unknown` is derived as fleet − reported ([`conn_coverage.go`](../server/internal/agentapi/conn_coverage.go)), which makes a restart correct by construction and moves a disconnecting device to `unknown` rather than out of the count. A summary carrying only coverage produced state, so it is no longer counted as a discarded message and the telemetry ledger keeps balancing. | EF-B7: correlation moves to the device | An alert says what crossed a line; the question straight after it — what else moved — was answered centrally by dragging a window on a chart and having the server rank that device's series out of VictoriaMetrics. Two things ended that: central telemetry is now a **60 s average per dim**, so a central ranking would rank exactly what averaging destroys (a ten-second I/O collapse barely moves the minute it sits in), and the endpoint was an on-demand telemetry pull at the moment a fleet is least able to serve several. The ranking now runs where the 1 s detail lives ([`correlate`](../agent/crates/mesh-agent-core/src/correlate/)) and travels with the alert, so the technician who opens FS01's incident already reads `disk.await_ms 0.91, cpu.total 0.84` — no operator action, no query. Three signals blend into one score in `[0, 1]`: KS distribution shift, the share of readings outside the baseline's band, and the mean shift against the baseline's own scale; **the third earns its place** because the first two saturate on any clean separation, so without it a service time that went 0.40 ms → 0.44 ms outranks one that went 0.4 ms → 40 ms. Weights are **behaviour, not tuning knobs**. The port was proven against a **reference ranking frozen before anything was deleted** ([`correlate_reference.json`](../agent/crates/mesh-agent-core/tests/fixtures/correlate_reference.json)): order, all four numbers to 1e-12, **and the tie-break** — score, then shape change, then label — because dimensions tie routinely (three fixture dims separate completely and differ only in how far they moved), and a primary-key-only check would pass on a fixture and diverge in production; a blend of doubles is compared within a tolerance rather than bit-for-bit, since a fused multiply-add may round once where two operations round twice. **Degenerate windows yield a number, never a NaN:** under two readings is left out rather than scored from nothing, a gauge flat all hour has no band so any different reading counts, an all-zero baseline has no scale so any nonzero mean is a full shift, and a non-finite reading is dropped where it enters — one place, so nothing downstream defends against it. Every run is bounded in **dimensions, readings and wall-clock**, the budget checked between dimensions so the first is always scored and the run always terminates with an answer plus a flag saying it was cut short; the read is an MVCC snapshot, so a correlation running while the sampler writes neither blocks ingestion nor sees a moving target. `/api/v1/devices/{id}/correlate` is **removed outright, not deprecated** — no external consumers, and its only caller retired in the same commit — along with `internal/correlate`, the handler, the generated Go/TS client, the drag UX, the chart's select hook and the freeze-poll it needed. No replacement drag is planned: the cursor reads values, presets choose the window, and the question the drag asked is answered before anyone asks it. | — | [edge-first-b7-edge-correlation-port.md](plans/archive/edge-first-b7-edge-correlation-port.md) |
| EF-B6: the failures that never cross a threshold | Every edge signal until now was a number crossing a line, and a whole class of failure never presents that way: a task blocked for two minutes, memory reclaimed by killing a process, a disk that stopped answering its bus, a processor slowing itself down under its own heat. The machine reports all of them about itself, in words, in its own log. Four curated Linux rules read them from the journal ([`event.rs`](../agent/crates/mesh-agent-core/src/alerts/event.rs)), beside a fifth that counts what no single record says — one service producing errors repeatedly inside a day. **The negative half is the half that earns its keep:** every subsystem that reports a failure also reports its recovery in nearly the same words about the same component, so each rule carries exclusions and a near-miss fixture, and a rule that matched on substrings alone would look green until it paged someone for a machine that just got better. The reader is a **bounded on-demand read, not a stream**, so the watch is a poll whose window deliberately overlaps the last one and re-presents records it has seen; a cursor makes that free, and the deliberate half of the cursor is that a record arriving late is **lost rather than duplicated** — an alert delivered twice costs more trust than one delivered never. A poll returning the reader's cap saw only the newest end of its window, so it is **counted as an event in itself** and no number of lost records is invented; records that cannot be placed in time and services the tracking cap turned away are counted separately, because three losses under one counter is a number that means nothing. A record a curated rule already explained does not also feed the per-service count, and records with no service attributed to them feed nothing rather than piling into one unnamed bucket that fires as though a single service were broken. Maintenance **suppresses** its window rather than deferring it: an admin rebooting a host produces exactly these records, and holding them would page someone for the maintenance itself. What the poll fetches is bounded by the level floor the pack states about itself, so a rule watching something less severe widens the read by existing rather than by anyone remembering to. Every alert is redacted before it exists — an alert is the one path that lifts a raw log line off a host outside the Logs pane — and all of them land in one bounded per-device sink ([`sink.rs`](../agent/crates/mesh-agent-core/src/alerts/sink.rs)) that drops its **oldest** entry when full and admits **20 per rolling hour**, both limits counting every alert they cost. The loss counts ride a log line with their running totals; carrying them on the wire belongs to the alert transport, which is where an alert starts leaving the device. | — | [edge-first-b6-event-rule-pack.md](plans/archive/edge-first-b6-event-rule-pack.md) |
| EF-B5: disk performance — how slow, not how full | Capacity answered "is the disk full" and nothing answered "is it slow", which is a different question about a different entity: capacity belongs to a **mount**, service time to a **physical device**. DAL-WS-012's NVMe wears out over a fortnight — service time drifting 2 ms → 40 ms while capacity is flat and CPU idle — and the technician reimages a healthy OS because every gauge the fleet collects says the machine is fine. Three vitals from the kernel's per-device I/O counters close it: `disk.await_ms`, `disk.await_ms.max`, `disk.queue_depth`, taking a Linux device to **exactly the 24-series cap** (the reserved headroom is now spent, so the next vital of any kind re-opens the cap). **No busy-percentage vital** — SSD/NVMe service many I/Os in parallel, so it pins at 100 % with headroom remaining, while queue depth keeps scaling and tells FS01's 02:00 backup (28 deep at a healthy 3 ms) apart from a device in trouble. **Worst device, per vital, independently**: the slowest device and the deepest queue routinely differ, and a mean across them describes neither; per-device detail rides alert evidence, so the reduction costs no cardinality. The device filter is the kernel's whole-block-device listing (partitions excluded by construction) minus `loop*`/`ram*`/`zram*`, with `dm-*`/`md*` **kept deliberately** because LUKS and RAID overhead is latency the user waits for. Service time ships a `.max` on the same arithmetic as `cpu.total.max` — a 5 s freeze moves a 3 ms average to 69 ms and pins the maximum at 800, which is what turns "the desktop froze at 12:05" into "the freeze was I/O-bound" — while queue depth, already a time-weighted average over the interval, ships none. A **VM needs no special handling** and guest-observed latency is the signal (host contention and volume throttling are exactly what makes the customer's application slow); a **containerized agent reports unsupported**, because the kernel's disk counters are not per-container and cgroup I/O accounting carries no service time to substitute — the container keeps a genuine I/O-stall signal through `stall.io.*`. **Never a wrong number:** counter wrap or reset, a device appearing or disappearing between readings, and a zero-length interval each yield nothing; a device that completed **no I/O has no service time**, because 0 ms would read as "instantaneous", while an empty queue is a real measurement. Readings publish at **milli resolution** (a 0.125 ms NVMe service time would round away at the percentage scale) and are quantized at the source, so the local store, the live window and alert evidence quote one number. Every path resolves under an **injectable filesystem root** — the container, a kernel without the counters, both kernel column layouts and every malformed line are fixture directories, and no test reads the reference host's own `/proc` or `/sys` — and the "am I containerized" question moved into one shared resolver so two collectors cannot disagree about it. | — | [edge-first-b5-disk-performance-vitals.md](plans/archive/edge-first-b5-disk-performance-vitals.md) |
| EF-B4: stall vitals from kernel pressure (Linux) | Utilization says how much of a resource is in use; it never says how much time work spent **blocked** on it, and the two diverge exactly when it matters. Five vitals — `stall.cpu.some`, `stall.mem.some`, `stall.mem.full`, `stall.io.some`, `stall.io.full` — are read from the kernel's pressure `avg60`, whose averaging window is exactly the 60 s the vitals contract publishes on, so each costs one file read and **zero cardinality**: the kernel already performed the reduction. A **containerized agent reads its own cgroup's** `*.pressure` and never falls back to host-wide `/proc/pressure`, which would report its neighbours' stalls as its own. Because a stall reading is *already* a 60 s average, its bucket publishes the **latest reading rather than the mean** — averaging sixty overlapping averages spreads the minute across two and damps the stall — and that rule lives in one series mapping applied by the live windower **and** reconnect-backfill, so live and gap-filled points for the same `(dim, ts)` stay identical. Every path resolves under an **injectable filesystem root**: the no-pressure host, the container, and every malformed kernel file are fixture directories, so the answer on a host without pressure is proven by an executed test rather than by inspection on a reference host that has it. | — | [edge-first-b4-stall-vitals-psi.md](plans/archive/edge-first-b4-stall-vitals-psi.md) |
