# Micro-Plan: Take web TypeScript to the current major (when upstream allows)

**Register entry:** [techdebt.md](../techdebt.md) — "`web/package.json` TypeScript
pinned to ^5.9.3 — `openapi-typescript` peer conflict." **Branch:** `dev`.
**Owner:** web. **Status:** **blocked upstream** — this is a watch + bump
procedure, not ready-to-implement. **Verified against npm 2026-09-23.**

## 1. Problem

TypeScript is pinned `^5.9.3` in [`web/package.json`](../../web/package.json) because
`openapi-typescript@7.13.0` (used by `npm run generate:api`) declares
`peerDependencies: { typescript: "^5.x" }`. A clean `npm ci` (the `node:24-alpine`
Docker build) fails hard with `ERESOLVE` on any newer major — reproduced. All other
deps from that Dependabot group landed; only the TypeScript major stayed back.

The published TypeScript major is **7.0.2**, so the pin is two majors behind. This
plan is deliberately written against "the current major" rather than a number,
because the number moved once already while the block stayed put.

## 2. Trigger (the precondition)

Proceed **only** once `openapi-typescript` ships a release whose `typescript`
peerDependencies range admits the current major. Check:

```
npm view openapi-typescript version
npm view openapi-typescript peerDependencies
npm view typescript version
```

If the peer range admits the published major, the block is cleared and this plan is
actionable. Until then, leave the pin and this plan parked.

## 3. Scope

**In:** bump `typescript` and `openapi-typescript` together; regenerate the OpenAPI TS
client; fix compiler breakages; prove `npm ci` is clean.
**Out:** unrelated dep bumps; runtime behavior changes.

## 4. File inventory

| File | Change |
|---|---|
| `web/package.json` | `typescript` → the current major; `openapi-typescript` → the release that admits it. |
| `web/package-lock.json` | Regenerated by `npm install`. |
| `web/src/types/api.d.ts` (or generated path) | Re-run `npm run generate:api`. |
| `web/**` | Any compiler-break fixes (likely lib/strictness changes). |

## 5. Approach

1. Confirm the trigger (§2).
2. Bump both deps; `npm install`; **then `npm ci`** to prove the `ERESOLVE` case is
   gone (mirror the Docker build: `node:24-alpine`).
3. `npm run generate:api` — confirm codegen still works against the OpenAPI spec.
4. `npx tsc -b` / `npm run build`; fix breakages. (`tsc --noEmit` checks nothing
   here: the root tsconfig is a solution file.)
5. Align `typescript-eslint` to a supporting version if needed; `npm run lint`.
6. commit → `/refactor` → commit → push.

## 6. Quality metrics / acceptance

- [ ] `npm ci` succeeds on the new major (the exact failure mode is gone).
- [ ] `npm run generate:api` produces unchanged-or-correct types.
- [ ] `tsc -b`/build/lint green; the `build-image` Docker build passes.
- [ ] The precommit gauntlet green.

## 7. NFRs

- **Maintainability:** keeps the toolchain current; unblocks deps that require the
  newer major.
- **Security:** newer TypeScript and `openapi-typescript` pick up upstream fixes; no
  new attack surface.

## 8. Reviewer checklist

- [ ] `npm ci` (not just `npm install`) verified clean.
- [ ] Generated API types reviewed for unexpected diffs.
- [ ] No `any` introduced to paper over new strictness (strict-mode rule).

## 9. Risks

- A new major may introduce strictness breaks across the app; budget fix time.
- Until the trigger clears, do not force-resolve the peer (no lenient overrides in CI).
